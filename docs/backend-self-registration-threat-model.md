# Backend Self-Registration & Backend Admin API — Threat Model (pre-implementation)

Status: **PRE-IMPLEMENTATION**. No code for this feature exists on `feature/backend-self-registration` (branched off `master` at `2b53292`). This model threat-models the approved-in-draft `docs/backend-self-registration-architecture.md` (`BSR-01..BSR-26`): the ADMIN write API (`POST /backends`, `DELETE /backends/{name}`), the WORKER-role `POST /backends/announce`, the `gateway.backend.self-registration.enabled` kill switch, the startup-enforced `allowed-host-pattern`, and the matching Worker-side announce-on-startup.

It **extends** `docs/threat-model.md` (`SR-01..SR-24`, `T-01..T-26`), `docs/worker-threat-model.md` (`WSR-01..WSR-18`, `WT-01..WT-16`) and `docs/worker-observability-and-claim-latency-threat-model.md` (`WOR-01..WOR-20`). It rewrites none of them. Requirement prefix per the architecture doc's header: threats **`BST-nn`**, requirements **`BSQ-nn`**.

Methodology: STRIDE per element/flow + OWASP Top 10 (2021) + CWE. Risk = qualitative Likelihood × Impact (Critical/High/Medium/Low). Every requirement is tagged MUST / SHOULD / ACCEPTED-RISK.

The **automatic-vs-approval** decision (option A over option B) is a settled user decision and is **not** re-litigated here. What is modelled is the concrete design as written, and what it takes for option A to be safe.

### Why this gets its own file

It creates the **first WORKER-role write path into a non-`review_*` table**, and the first path by which a fleet-shared token can influence an outbound network destination the Gateway will then contact on a schedule. `docs/threat-model.md`'s `T-07`/`SR-10` modelled `backends.url` as *DBA-written data that must still be re-validated*; this feature makes it *caller-supplied data*. That is a category change in the SSRF model, not an increment, and it needs one citable place.

## 1. Decomposition

### New / changed elements

| Element | Change | Module |
|---|---|---|
| `POST /backends/announce` + `BackendAnnounceController` | **New**, WORKER-role, `@ConditionalOnProperty` | Gateway |
| `POST /backends` / `DELETE /backends/{name}` on `AdminController` | **New**, ADMIN-role write surface | Gateway |
| `BackendRegistryService` | **New** — the only writer of `backends` outside `BackendHealthChecker` | Gateway |
| `backends.announced_by` (`V6`) | **New** nullable column, self-registration ownership | Gateway |
| `BackendRepository.findByNameForUpdate` | **New** `PESSIMISTIC_WRITE` read | Gateway |
| `BackendUrlValidator` | Unchanged code, **new caller** on a request thread with caller-supplied input | Gateway |
| `gateway.backend.self-registration.enabled` + `validateBackendSelfRegistrationOnStartup()` | **New** flag + startup gate on `allowed-host-pattern` | Gateway |
| `SecurityConfig` / `RequestBodySizeLimitFilter` / `WebConfig` | New matchers, new body cap, **new url-pattern registration** | Gateway |
| `MetricsCounters.backendAnnounceRejected` | **New** `Map<String,AtomicLong>` counter | Gateway |
| `backend.url` / `BACKEND_URL`, `GatewayClient.announce`, `WorkerRunner` announce step | **New** | Worker |

### Trust boundaries (delta on `threat-model.md` §1 and `worker-threat-model.md` §2)

| # | Boundary | Channel | Trust posture |
|---|---|---|---|
| **BSTB-ANN** | Worker → Gateway, `POST /backends/announce` | HTTPS, `Authorization: Bearer WORKER_TOKEN` | **New and the whole point of this model.** The token is shared across the entire Worker fleet (T-15/WT-16). "Authenticated" means "someone in the fleet, or whoever holds a stolen fleet token" — never "the legitimate owner of `backendId`". `backendId`, `workerId`, `url`, `model` are all untrusted claims. |
| **BSTB-URL** | `backends.url` → outbound `GET {url}/health` from the Gateway host, every 60 s, forever | Gateway → arbitrary allowlisted host | **Category change.** Previously DBA-written; now caller-supplied. This is a persistent, scheduled, semi-blind SSRF primitive whose destination the caller chooses once and the Gateway re-uses indefinitely. |
| **BSTB-ADMIN** | Operator → `POST /backends` / `DELETE /backends/{name}` | HTTPS, `ADMIN_TOKEN` | **New write surface on the highest-privilege token.** Same SSRF sink, different (trusted) principal. Detailed error messages are acceptable here (BST-11). |
| **BSTB-AUDIT** | Registry mutations → slf4j only | in-process | **New and thin.** `review_events.review_id` is `NOT NULL REFERENCES reviews(id)` (`V1:76-77` equivalent for jobs; verified for events), so no DB audit row is possible. Log files are the *entire* audit trail for who repointed a production backend (BST-12). |
| **BSTB-BOOT** | Gateway config → startup refusal | operator config | **New.** `allowed-host-pattern` stops being an optional hardening knob and becomes a load-bearing security control that an operator must author by hand, for the first time (BST-03, BST-04). |

### Assets (delta)

- **A-REG** — the `backends` registry: which hosts the Gateway will contact, at what rate, on whose behalf. Previously write-restricted to a DBA; now fleet-token-writable.
- **A-NET** — the Gateway host's network position (it sits where it can reach both GitLab over HTTPS and the LAN llama-servers). A repointable outbound GET from that position is the asset an SSRF actually buys.
- **A-CAP** — dispatch capacity and outage detection. `BackendHealthChecker.probeAll()` is **serial** over all `ACTIVE`+`SUSPECT` rows with a 10 s read timeout; the row count is now caller-controlled (BST-08).
- **A-AUD** — attribution of registry changes. Log-file-only (BSTB-AUDIT).

### Flow

```
 Worker startup (WorkerRunner.run, before workerLoop.start(), before ACCEPTING_TRAFFIC)
        │  backend.url set?  no ──► INFO, legacy mode, start loop
        ▼ yes
 POST /backends/announce {backendId, workerId, url, model}     ──► BSTB-ANN
        │
        ▼ SecurityConfig: hasRole("WORKER")  (matcher present only when flag=true)
 BackendAnnounceController (@ConditionalOnProperty)
        │ bean validation (charset/length)
        ▼
 BackendRegistryService.announce
        │ BackendUrlValidator.validate(url, allowedHostPattern)
        │     └─ InetAddress.getByName(host)   ──► DNS from the Gateway's network  (BST-05/06)
        │     └─ host.matches(operatorRegex)                                        (BST-03/04)
        │ findByNameForUpdate  ──► §2.4 decision table                              (BST-01/07)
        │ INSERT (unbounded row count)                                              (BST-08)
        ▼
 backends.url  ──► BackendHealthChecker (every 60 s, serial, 10 s read timeout)
        └─► BackendProberImpl:  GET (url + "/health")   ── string concat            (BST-02)
```

## 2. STRIDE threats — BST-01..BST-19

| # | STRIDE | OWASP / CWE | Element | Description | Risk | Status |
|---|---|---|---|---|---|---|
| **BST-01** | Elevation / Tampering | A01, A10 / CWE-284, CWE-639 | §2.4 decision table, row 2 (`announced_by IS NULL`) | **Day-one mass repoint.** `V6` adds `announced_by` as `NULL` for *every existing row*, and every backend in every current deployment was registered by raw SQL — i.e. every production backend starts life in the **most permissive branch** of the decision table. The first thing that happens after `self-registration.enabled=true` is that any fleet-token holder can `POST /backends/announce {backendId:"mac-mini-01", workerId:"anything", url:"http://<any-allowlisted-host>:<any-port>"}` and silently repoint a live `ACTIVE` production backend, with **no `409`, no operator action, and the response `200 {created:false}`**. The doc's own §7 residual concedes "create/repoint a row for a name it owns **or that is unowned**" but does not surface that "unowned" is the universal initial state. The `409` guard protects only rows a *different* Worker has already claimed — i.e. none, on day one. | **High** | **Needs mitigation** (New) |
| **BST-02** | SSRF / Tampering | A10 / CWE-918, CWE-20 | `BackendProberImpl:46` + unconstrained `url` | **The "bare health GET" claim is not enforced anywhere.** `BackendUrlValidator` validates scheme and host only — path, query, fragment, userinfo and port are entirely unconstrained, and `@Size(max=256)` is the only other bound. The prober does `.uri(backend.getUrl() + HEALTH_PATH)` — plain string concatenation. So `http://allowed-host:8080/admin/reset?x=` becomes `GET /admin/reset?x=/health`: **an arbitrary path, with an arbitrary query, on an arbitrary port of any allowlisted host, repeated every 60 s forever.** Redirects are off and the body is discarded, so it is blind — but blind is sufficient for state-changing GETs, port/service scanning across the allowlisted range (200-vs-connection-error is inferable from `SUSPECT` flips and `GET /backends`), and keeping an internal service under constant load. Note also `RestClient.uri(String)` treats the argument as a URI *template*, so a `{` in a stored url throws inside the scheduler thread. This is the largest gap between the doc's stated blast radius and the real one. | **High** | **Needs mitigation** (New / Found) |
| **BST-03** | SSRF / bypass of the mandatory mitigation | A05, A10 / CWE-183, CWE-1287 | BSR-12 sentinel check | **The sentinel test proves "not literally universal", never "narrow" — and the doc's three-sentinel set is trivially passable while still matching every internal target.** All of these pass `{evil.example.com, metadata.google.internal, a3f9c1e2-probe.invalid}` and start the Gateway: `^[0-9.]+$` (matches *every* IPv4 literal — all of RFC1918, all of CGNAT `100.64/10`, every public address, and the operator will read it as "only IPs, that's narrow"); `^[^.]*$` (every single-label internal hostname); `.*\.(com\|internal)$`; `^(?!.*\.invalid$).*$`. The first is not a contrived attack — it is a *plausible thing a hurried operator writes*, and it is effectively `.*` over the whole IPv4 space. Making the check the headline mitigation while it cannot detect its own most likely failure mode is exactly the "false assurance" pattern the doc itself invokes FW-01 against. | **High** | **Needs mitigation** (New) |
| **BST-04** | DoS | A05 / CWE-1333, CWE-400 | `BackendUrlValidator:57` | **ReDoS on an operator-authored regex against caller-supplied input.** `host.toLowerCase(ROOT).matches(pattern)` recompiles the pattern on every call and runs it against a host of up to ~250 characters that the *caller* chooses. Java's regex engine is backtracking with no timeout. BSR-12 is the first thing in this project's history to *force* every self-registration operator to hand-author a regex, so the population of hand-rolled patterns — and the odds of nested quantifiers — goes from "one example in DEPLOYMENT.md" to "one per deployment". Two sinks: a Tomcat request thread per announce (cheap, repeatable, authenticated), and the single `BackendHealthChecker` scheduler thread on every probe pass (which also wedges outage detection for every other backend). A host length cap alone does **not** fix this — 250 characters is far past the point where catastrophic backtracking is fatal. | Medium | **Needs mitigation** (New) |
| **BST-05** | Info disclosure / SSRF | A01, A10 / CWE-203, CWE-918 | `isBlockedHost` DNS lookup + `200`/`422` status split | **The `422` message collapse is correct but only removes ~2 bits; the oracle survives in three other channels.** (a) The *status code* still separates accepted from rejected, so a fleet-token holder reconstructs `allowed-host-pattern` at 1 bit per request, unrate-limited. (b) `InetAddress.getByName` fires a **real DNS query from inside the Gateway's network** for every submitted host — an unauthenticated-to-the-resolver out-of-band channel (internal-resolver reachability, split-horizon zone enumeration, plain exfiltration in the QNAME) that no HTTP-level message collapsing can close. (c) A *successful* announce converts the blind guess into an actual scheduled HTTP GET — full SSRF confirmation. Secondary: `getByName` has no timeout, so a hostile authoritative nameserver holds a Tomcat request thread open. | Medium | **Needs mitigation** (New; bounded, not closable) |
| **BST-06** | Tampering (TOCTOU) | A10 / CWE-367, CWE-918 | `isBlockedHost` vs. connect-time resolution | DNS rebinding: the loopback/link-local block resolves at validate time; `BackendProberImpl` resolves again at connect time, 60 s later and every 60 s after. A name whose A record flips to `127.0.0.1`/`169.254.169.254` defeats the block entirely. Additionally `getByName` returns only the **first** address — a name with one public and one loopback A record can pass the check and connect to either. Pre-existing under `SR-10`, but until now the hostname was DBA-chosen; this feature makes it caller-chosen, which is the precondition the attack actually needs. | Medium | **SHOULD + accepted residual** (Amp of T-07) |
| **BST-07** | Spoofing / Elevation | A01, A07 / CWE-290, CWE-345 | `announced_by` = request-body `workerId` | The doc's self-assessment ("misconfiguration guard, not a security control") is **honest and confirmed** — `workerId` is body-supplied under a shared token with no binding whatsoever (T-03/T-15/WT-16). Two things to nail down so it does not silently become a boundary: (a) the `200`-vs-`409` split is itself an *ownership oracle* — announcing a guessed `workerId` returns `200` and repoints the URL if the guess is right, and `workerId` values are low-entropy operator strings (the doc's own example, `worker-mac-mini-01`, is mechanically derivable from `backendId`); (b) the implementation checklist's item 10 tests the four decision-table rows, which is exactly how a *functional* guard acquires the appearance of an *authz* test in a later reviewer's eyes. | Medium | **Needs mitigation** (documentation + detection, not enforcement) |
| **BST-08** | DoS / Spoofing | A04 / CWE-770, CWE-400, CWE-799 | INSERT branch of announce | **Unbounded authenticated row-creation on `backends`, amplified by the health checker.** Nothing in the design caps how many rows announce may create; `backendId` has a 64-char alphanumeric space. This is a strictly *cheaper* and *more damaging* abuse primitive than the `/jobs/{id}/heartbeat` INSERT primitive `WOT-15` assessed as the floor. | **High** | **Needs mitigation** (New) |
| **BST-09** | DoS | A04 / CWE-770 | `RequestBodySizeLimitFilter` + `WebConfig` | BSR-15 says to add patterns to the filter. That is **necessary but not sufficient**: `WebConfig.requestBodySizeLimitFilter` registers the filter with `addUrlPatterns("/reviews", "/jobs/*")`, so the container will never invoke it for `/backends` regardless of what `limitFor()` returns. Implementing BSR-15 as literally written ships a *silently uncapped* endpoint that looks capped in review and in a unit test of the filter class. | **BST-10** | Elevation of privilege | A01 / CWE-285, CWE-863 | `SecurityConfig` + `@ConditionalOnProperty` | Two independent reads of the same flag (`SecurityConfig`'s `if` and the controller's `@ConditionalOnProperty`) can disagree — relaxed binding, a profile override, a typo in the `havingValue` prefix. Both disagreement directions happen to fail closed today (matcher without controller ⇒ `404`; controller without matcher ⇒ `denyAll` `403`), which is correct but **accidental**, and the `403`-when-disabled contract the Worker's terminal-failure messaging depends on (BSR-20) is only true in one of them. | **BST-11** | Info disclosure | A01, A09 / CWE-209, CWE-532 | `422` message split (WORKER vs ADMIN); §6 log fields | The WORKER-side collapse is **justified** (it removes the "blocked range" vs "allowlist mismatch" distinction, which is a direct read on the operator's internal network shape) — but it is *marginal*, not sufficient, per BST-05, and the design must not be credited with more than it buys. The ADMIN-side detailed message is **also justified**, but not for the reason implied: there is no ADMIN-specific audit or access control that makes it safe. Adding a caller-writable path to this table is the right moment to narrow it. Also note `SR-19`'s append-only discipline exists for `review_events`/`review_prompt_sections` only; `backends` has never needed it and still does not, but the asymmetry should be a decision, not an oversight. | Low | **SHOULD** (Found) |
| **BST-17** | Info disclosure | A01 / CWE-200 | new response DTOs | `T-17`'s minimization is real and currently intact (`BackendView`/`BackendSnapshot` carry no `url` — verified). The natural implementation of `POST /backends` echoes the submitted body back, which would put `url` into an ADMIN response and, one refactor later, into `GET /backends`. ## 3. Deep dives

### 3.1 Is the `allowed-host-pattern` fail-fast sufficient? — **No, and it cannot be made sufficient**

The check answers "does this pattern match everything?", which is a *decidable-by-sampling* question only for the sample you chose. It cannot answer "is this pattern narrow enough for the Gateway's actual network position", which is the question that matters. BST-03's `^[0-9.]+$` case is the proof: it fails every name-shaped sentinel, passes the gate, and grants the whole IPv4 space.

The right response is **not** to abandon it — it does reliably catch the literal `.*` default, `.+`, `[\s\S]*`, `(?s).*`, blank, and every "I'll tighten this later" placeholder, which is the single most likely real-world failure. The right response is to (a) widen the sentinel set so it also catches the *IP-shaped* universal patterns, (b) stop describing it as "the actual mitigation", and (c) put a real, non-regex bound underneath it. The real bound available for free is BST-02's fix: if `url` is normalized to a bare `scheme://host[:port]` origin, then the worst a maximally-wrong pattern buys is `GET /health` against arbitrary hosts — recoverable and low-value — instead of arbitrary-path GETs.

Minimum robust sentinel set (all must fail to match, else refuse to start): a name-shaped host, a cloud-metadata name, a random-label host under a random TLD, **and** IP literals covering every "an operator thinks this is narrow but it isn't" shape — `10.0.0.1`, `172.16.0.1`, `192.168.0.1`, `100.100.100.200`, `8.8.8.8`, `203.0.113.7`, `169.254.169.254`. A pattern that matches *all* of those is universal in every sense that matters here.

### 3.2 The `409 BACKEND_NAME_TAKEN` framing

Confirmed honest, and confirmed correctly de-credited in §2.4/§7. The failure mode to prevent is not the doc's reasoning — it is the *implementation and test artefacts* re-crediting it: a test named `announce_cannotTakeOverAnotherWorkersBackend` reads like an authz test, and a future reviewer will treat it as one. Hence BSQ-06's requirement that the code comment and the test name both say "misconfiguration guard", and that the SAST round re-checks that no other control's argument depends on it. Note that BST-01 is the concrete demonstration that it is not a boundary: on day one it blocks nothing at all.

### 3.3 The `422` collapse (WORKER) vs. detailed message (ADMIN)

Necessary: yes — the five validator messages separate *DNS resolution outcome* from *allowlist membership*, which is a direct read on internal topology, and it is free to collapse them. Sufficient: no (BST-05). Correct for ADMIN: yes, but on privilege grounds and constant-string grounds, not on audit-logging grounds — there is no ADMIN-specific audit today, and BSR-24's ADMIN log line is a single INFO with no more coverage than the WORKER lines. Do not let the design claim otherwise.

### 3.4 Audit logging (§6)

The field list is clean — no token, no full URL, no stack trace, fixed-vocabulary counter keys matching the `structuredValidationFailures` precedent (verified: `MetricsCounters` already uses `Map<String,AtomicLong>` with `computeIfAbsent`). Three corrections: host:port-vs-URL is cosmetic **only after** BST-02 is fixed (before that it is a forensic own-goal); the scheme must be logged because `http` is accepted (BST-13); and every field read back from a *DB row* rather than from a freshly-validated DTO (a legacy SQL-registered `name`/`model`, an `announced_by` written before `V6`'s conventions) must go through `TextSanitizer.sanitizeSingleLine` — the doc says "CR/LF-stripped", the existing helper does strictly more (Cc/Cf/Zl/Zp + cap) and already exists.

### 3.5 The DB grant (BSR-26)

BSR-26's premise is false against the documented deployment (`INSERT` is already granted, table-level, so `announced_by` is covered and no sequence grant is needed). It survives as a *verification* item because the doc's own hedge — "verify this against the actual deployed role rather than assuming" — is the correct instruction for a role that may have drifted. Since Flyway does not manage GRANTs in this project, the migration is the only artefact an operator is guaranteed to read at upgrade time, so the reminder belongs in it as a comment. The genuinely actionable grant finding is the opposite one, BST-16: `DELETE` on `backends` is granted and never used.

### 3.6 Independent non-negotiable-principle check

Beyond the architect's §7 self-check:

- **Gateway is the sole owner of business logic and state** — holds. Every field the Worker can influence is validated Gateway-side; status/capacity/mode columns are unreachable from the WORKER path. Confirm in code review that `BackendRegistryService.announce` writes a fixed field set and never `Backend` fields by reflection/mapper.
- **PostgreSQL is the single source of truth** — holds for *state*, **not** for *provenance* (BST-12). Registry state is fully reconstructible after a restart; who set it is not, once logs rotate. Call it out rather than let §7's clean "Holds" stand unqualified.
- **Idempotency everywhere a retry can happen** — the design is right, the stated implementation is not (BST-18).
- **No extra infrastructure** — holds; nothing here needs a new dependency, thread, scheduler or table. BSQ-13's row cap is a `count()`, BSQ-04's ReDoS budget is a `System.nanoTime()` around one `matches()` at startup.
- **Fail fast at the edge** — holds in intent, breaks in one place (BST-09: the cap is registered where it will not run).
- **Gateway restarts must not disturb in-flight work** — holds; nothing reads or writes `review_jobs`.
- **Worker is a fully stateless HTTP client** — holds; the announce is one more call on the existing `gatewayRestClient` with the existing token and nothing cached. BST-14(a) is the one place where the *Worker* starts making a Gateway-side policy decision (treating `403` as fatal) that it has no business making.

## 4. Security requirements — BSQ-01..BSQ-24

### The blocking set: registry write authority

- **BSQ-01 (MUST, BST-01).** An announce against an **existing** row whose `announced_by IS NULL` may take ownership (set `announced_by = workerId`) **only if it does not also change `url`**. A first-claim announce that carries a different `url` than the stored one is rejected `409 BACKEND_NAME_TAKEN` with zero mutation, WARN, and a counter increment. Rationale: `INSERT` (fresh name) and "re-announce a row I already own with a new address" both keep working — the self-healing story is untouched — while the day-one mass-repoint of every SQL-registered production backend becomes a no-op. `model` may be updated on a first claim (it is not a network destination). The documented remedy for a legitimately-changed address on an unowned row is the existing one-admin-call escape hatch (`POST /backends {name,url,…}`, which clears `announced_by` and rewrites `url` under ADMIN authority). *Test:* pre-existing `ACTIVE` row, `announced_by = NULL`, announce with a different `url` ⇒ `409`, row byte-identical; same announce with the identical `url` ⇒ `200`, `announced_by` set; a subsequent announce from that owner with a new `url` ⇒ `200`, `url` updated.
- **BSQ-02 (MUST, BST-01/BST-12).** Any transition of `announced_by` from `NULL` to a value, and any `url` change on any path, logs a dedicated **WARN** line (not the generic "updated" INFO) carrying `name`, `workerId`, old origin and new origin, and increments a counter. These two are the security-relevant mutations; they must not be indistinguishable from a routine no-op re-announce in the log stream.
- **BSQ-03 (MUST, BST-08).** A hard cap on registry size, enforced inside the announce INSERT branch under the same transaction: refuse to create a new row when `backendRepository.count()` is at or above `gateway.backend.self-registration.max-backends` (default **16** — the scale target is 1–10). Rejection is `409`/`422` with a fixed message, a WARN naming the cap, and a counter. Admin `POST /backends` is **not** subject to the cap (trusted principal, and an operator must always be able to fix things). *Test:* announce with `max-backends` rows present ⇒ rejected, no INSERT, counter incremented; the same request via the ADMIN path ⇒ succeeds.

### The blocking set: SSRF blast radius

- **BSQ-04 (MUST, BST-02).** `url` is **normalized to a bare origin before persistence** on both write paths: `scheme://host[:port]`, with any path, query, fragment or userinfo present in the submitted value causing rejection (WORKER: fixed `422 BACKEND_URL_REJECTED`; ADMIN: a specific constant message). Do not silently strip — rejecting is the honest signal, and the Worker's `backend.url` should never contain a path anyway. Enforce it in `BackendUrlValidator` itself, not in the DTO, so the probe path re-validates it on every use exactly as it re-validates the host today (this preserves the `SR-10` "validated on every use, not just at write time" property, and neutralizes legacy rows on the next probe pass). *Test:* `http://h:8080/admin?x=` , `http://h:8080/`, `http://u:p@h:8080`, `http://h:8080#f` are each rejected; `http://h:8080` and `http://h` are accepted; a legacy row with a path fails its next probe rather than being probed.
- **BSQ-05 (MUST, BST-03).** The BSR-12 sentinel set is extended to include IP-literal sentinels covering every private/CGNAT/metadata/public shape — at minimum `10.0.0.1`, `172.16.0.1`, `192.168.0.1`, `100.100.100.200`, `169.254.169.254`, `8.8.8.8`, `203.0.113.7` — alongside the existing name-shaped ones, and a randomly-generated label under a randomly-chosen TLD so a pattern cannot be tuned to a hard-coded list. Refuse to start if the pattern matches **all** sentinels. The startup failure message and the `DEPLOYMENT.md` text must both state plainly that **passing this check is not evidence the pattern is narrow** — it only proves it is not universal. *Test:* `.*`, `.+`, `.*.*`, `[\s\S]*`, `(?s).*`, `^[0-9.]+$`, `^[^.]*$`, `^(?!.*\.invalid$).*$` and blank all refuse startup; `^192\.168\.1\.\d+$` starts.
- **BSQ-06 (MUST, BST-04).** The allowlist pattern is compiled **once**, at startup, into a `Pattern` held on `GatewayProperties.Backend` (or a small holder bean) and reused — never recompiled per call — and a `PatternSyntaxException` refuses startup regardless of whether self-registration is enabled. At startup, immediately after compilation, run the pattern against a pathological input (e.g. 255 repetitions of `a`, and 255 of `a` followed by `!`) under a wall-clock budget of 100 ms; exceeding it refuses to start with a message naming the property and the word "catastrophic backtracking". Additionally reject a host longer than 255 characters before matching. *Test:* `^(a+)+$` refuses startup; a benign pattern starts; the compiled pattern instance is identical across two `validate` calls.
- **BSQ-07 (MUST, BST-02/BSQ-04).** `BackendProberImpl` keeps building the probe URI by concatenation only because BSQ-04 guarantees a bare origin — add an assertion/comment binding the two, and a test that a stored url containing `?`, `#`, or `{` never produces a request to a path other than `/health` (today `{` throws inside the scheduler thread; after BSQ-04 it cannot be stored, and the probe-time re-validation rejects a legacy one).

### Concurrency, correctness and the write path

- **BSQ-08 (MUST, BST-18).** The insert-race retry lives **outside** the transaction. Structure it as `QueueManager.reportFailure`/`WOC-26` does: a non-`@Transactional` orchestrator method calls a `@Transactional(propagation = REQUIRES_NEW)` inner method, catches `DataIntegrityViolationException` from the *completed* inner call, and re-invokes it exactly once. Never catch the violation inside the transaction that caused it. Use find-then-`save()`, never a native `INSERT … ON CONFLICT` (which would bypass `Backend.name`'s `updatable = false` and the `@PreUpdate` timestamp). *Test:* two concurrent announces of the same new name both terminate, one `created:true` and one `created:false`, neither a `500`; a forced double-violation surfaces as `500` rather than looping.
- **BSQ-09 (MUST).** `BackendRegistryService.announce` writes an explicit, hard-coded field set — `url`, `model`, `announced_by` (and, on INSERT only, `status = ACTIVE`, `capacity = 1`) — by direct setter calls. No bean-mapping, no reflection, no `BeanUtils.copyProperties`. `status`, `capacity`, `structured_output_mode`, `prompt_message_format`, `probe_failed_since` and `last_seen` are unreachable from the WORKER path by construction, not by omission. *Test:* an announce body carrying extra JSON fields (`status`, `capacity`, `structuredOutputMode`) changes none of those columns; `spring.jackson.deserialization.fail-on-unknown-properties` behaviour is asserted either way.
- **BSQ-10 (MUST, BST-07).** `announced_by` ownership is documented **in the code** (`BackendRegistryService` javadoc and the `V6` column comment) as a misconfiguration guard, never an authorization boundary, citing T-03/T-15/WT-16. Test names for the §2.4 table use guard language (`announce_differentWorkerId_isBlockedAsMisconfiguration`), not authz language. *Verify:* SAST round greps for any control whose stated argument depends on the `409`.

### Edge, routing and caps

- **BSQ-11 (MUST, BST-09).** The body cap is wired **end to end**: `WebConfig.requestBodySizeLimitFilter` gains `/backends` and `/backends/*` url-patterns **and** `RequestBodySizeLimitFilter.limitFor` gains the corresponding `PathPattern`s with the 8 KiB constant. Register both unconditionally, regardless of the feature flag — a cap on a path that returns `403` costs nothing and cannot drift out of sync with the flag. *Test:* a 9 KiB `POST /backends/announce` returns `413` **through the running application context**, not through a direct unit test of the filter class; the same assertion for `POST /backends`.
- **BSQ-12 (MUST, BST-10).** A full role matrix test over `POST /backends`, `DELETE /backends/{name}`, `POST /backends/announce` × {no token, CI, WORKER, ADMIN} × {flag on, flag off}, asserting exactly one role reaches each path and everything else is `401`/`403` — including `POST /backends/` (trailing slash) and `/backends/%61nnounce`, which must not reach a handler under a rule different from their canonical forms. The flag is read from **one** place (`GatewayProperties`) by both `SecurityConfig` and the `@ConditionalOnProperty`; a test asserts the property name string is identical in both. *Test:* the matrix exists and covers all 24 cells.
- **BSQ-13 (MUST, BST-11/SR-17).** Every `BackendUrlValidator` message stays a compile-time constant with no interpolated input; the WORKER path maps all of them to one fixed `422 BACKEND_URL_REJECTED` body; `GlobalExceptionHandler.handleValidation` continues to emit `field + ": " + defaultMessage` and never `getRejectedValue()`; no `@Pattern`/`@Size` message on a new DTO uses `${validatedValue}`. *Test:* every distinct rejection cause on `POST /backends/announce` yields a byte-identical response body; a `400` on a malformed `url` does not contain the submitted value.

### Logging, detection and audit

- **BSQ-14 (MUST, BST-11/BST-12/§3.4).** Log lines carry `scheme://host[:port]` (not `host[:port]` alone, and not the full URL — which after BSQ-04 are the same thing modulo scheme), never a token, never a stack trace. Every value read from a DB row rather than from a just-validated DTO passes through `TextSanitizer.sanitizeSingleLine(value, cap)` before reaching a placeholder. *Test:* a `backends` row seeded with `name = "a\r\nFAKE INFO evil"` produces a single log line.
- **BSQ-15 (MUST, BST-01/BST-05/BST-07/BST-08).** `MetricsCounters.backendAnnounceRejected` is a `Map<String,AtomicLong>` over a **closed Gateway-side vocabulary** — `NAME_TAKEN`, `URL_REJECTED`, `VALIDATION`, `REGISTRY_FULL` — never a backend name, `workerId` or URL, exposed through `MetricsSnapshot`/`MetricsResponse`/`GET /metrics` (ADMIN). Add a second counter `backendUrlRepointed` for BSQ-02's WARN condition: an allowlist-probing or repoint campaign must be visible as a number, since it will not be visible as a DB row. *Test:* each rejection cause increments its own key; an accepted repoint increments `backendUrlRepointed`; no key derived from request input ever appears.
- **BSQ-16 (MUST, BST-12).** `DEPLOYMENT.md` states explicitly that backend-registry mutations are audited **in log files only** (with the reason: `review_events.review_id` is a `NOT NULL` FK), that `backends.updated_at` is overwritten by the next health probe and is not an audit trail, and therefore that Gateway log retention is the audit retention for this feature. No new table, no nullable FK, no synthetic Review — the design decision stands; only its consequence needs stating.
- **BSQ-17 (MUST, BST-17).** `POST /backends` and `DELETE /backends/{name}` respond with the existing url-free `BackendView`, constructed from the persisted entity — never by echoing the request DTO. *Test:* the `POST /backends` response body contains no `url` field even though the request did; an architecture/grep test asserts `Backend.getUrl()` has no call site outside `BackendProberImpl` and `BackendRegistryService`.

### Worker side

- **BSQ-18 (MUST, BST-14a).** `403` and `404` from `POST /backends/announce` are **WARN-and-continue**, not terminal: log one WARN naming the likely cause (Gateway's `self-registration.enabled` is off, or the token is not the WORKER token), then `workerLoop.start()`. `409` and `422` stay terminal (`IllegalStateException`, non-zero exit) — they are this Worker's own misconfiguration and never self-heal. Rationale: `403` is functionally identical to BSR-17's supported legacy mode; treating it as fatal makes a Gateway-side kill switch a fleet-wide outage button. *Test:* a stubbed `403` ⇒ WARN, loop starts, exit code 0; `409`/`422` ⇒ startup fails with the cause-specific message.
- **BSQ-19 (MUST, BST-14b).** The announce backoff loop is bounded and interruptible: it checks a `volatile` shutdown flag set from a `@PreDestroy`/`ContextClosedEvent` listener on each iteration, sleeps in slices no longer than one backoff step, and propagates `InterruptedException`. A `SIGTERM` during the loop must terminate the process within the container's normal shutdown budget rather than requiring `SIGKILL`. *Test:* a unit test that closes the context mid-backoff observes the loop exit.
- **BSQ-20 (MUST, BSR-18).** `WorkerProperties.validateBackendUrl()` implements all four stated rules, reusing the existing private `isLoopbackHost`, and additionally rejects a `backend.url` carrying a path/query/fragment/userinfo — mirroring BSQ-04 so the Worker fails at startup with a precise message instead of collecting an opaque `422`. Its javadoc records that `isLoopbackHost` is a string check, so a LAN name that *resolves* to loopback will still be rejected Gateway-side; that asymmetry is intended, not a bug. Never echo the value in any message.

### Accepted residuals

- **BSQ-INH-1 (ACCEPTED-RISK, BST-05/BST-06/BST-07) — T-03 stays open, and this feature widens it.** `backendId`/`workerId` remain self-declared under a single fleet-shared `WORKER_TOKEN`. What that token can do grows from "claim jobs under any backend name" to "**also** create a registry row for any unused name, and repoint a row it owns". Bounded by: the kill switch (default off), the startup-enforced allowlist (BSQ-05/06), bare-origin normalization (BSQ-04), the registry cap (BSQ-03), first-claim URL immutability (BSQ-01), and detection (BSQ-02/15). The clean fix remains T-03's `SHOULD` — one token per backend with a token-bound `backendId`, at which point `announced_by` could become a real boundary. Explicitly out of scope; recommended as the first item of the follow-up branch.
- **BSQ-INH-2 (ACCEPTED-RISK, BST-05).** Announce remains an allowlist-membership oracle at 1 bit per request, and an outbound-DNS primitive from the Gateway's network position, for any fleet-token holder. Not closable at the HTTP layer (the DNS lookup happens before any response is chosen). Compensated by BSQ-15's counters and by `SR-20` (per-token rate limiting), which stays an unimplemented tracked `SHOULD` and gains one more endpoint's worth of justification here.
- **BSQ-INH-3 (ACCEPTED-RISK, BST-06).** DNS rebinding and multi-A-record hosts defeat the loopback/link-local block between validate and connect. **SHOULD**, cheap and recommended within this branch: switch `isBlockedHost` to `InetAddress.getAllByName` and reject if **any** returned address is blocked. That closes the multi-record case for a two-line change; genuine time-of-use rebinding remains open and is accepted (closing it needs pinned-IP connections, which is disproportionate at this scale).
- **BSQ-INH-4 (ACCEPTED-RISK, BST-13) — `SR-15`'s backend-url half is knowingly not enforced.** `http://` backend URLs remain accepted, because the LAN llama-servers have no TLS and the socket is unauthenticated by design (`WSR-06`/`WA5`). Record it as an explicit deviation from a MUST in `DEPLOYMENT.md` and `README.md` §4.3 — not as an oversight — and log the scheme (BSQ-14) so an `http` backend is visible in the operator's own logs.
- **BSQ-INH-5 (ACCEPTED-RISK, BST-15).** Parking a backend at `MAINTENANCE`/`OFFLINE` does not protect its `url` from announce. Harmless today (no code reads a non-`ACTIVE` row's url — verified) and documented, so an operator does not mistake parking for a write lock.

### SHOULDs

- **BSQ-21 (SHOULD, BST-16).** Narrow the documented grant: `REVOKE DELETE ON backends FROM review_gateway` (no code path deletes a backend row, and §5's "hard delete cannot be offered" then holds at the DB layer too). Keep `INSERT`/`UPDATE`/`SELECT`.
- **BSQ-22 (SHOULD, BSR-26/§3.5).** `V6__backend_self_registration.sql` carries a comment reminding the operator that Flyway does not manage GRANTs in this project and that `INSERT` on `backends` must be verified against the *deployed* role (already present in `DEPLOYMENT.md`'s documented grant, and table-level so `announced_by` is covered automatically — but roles drift). `DEPLOYMENT.md`'s grant block gets the same note.
- **BSQ-23 (SHOULD, BST-08).** When the registry is at or near `max-backends`, or when `probeAll()` exceeds its interval, the existing `WOC-17` skip WARN is enough signal — but add the current registry size to that WARN so "why did outage detection stop" resolves in one line instead of a DB query.
- **BSQ-24 (SHOULD).** Keep `String.matches` (full-match) semantics in `BackendUrlValidator`; a test asserts that a pattern like `^192\.168\.1\.\d+$` does not accept `evil.com/192.168.1.5` style hosts and that no `Matcher.find()` is introduced.

## 5. Architecture-level corrections required BEFORE dev starts

Changes to the approved-in-draft `docs/backend-self-registration-architecture.md`. Items 1–5 are blocking; 6–9 are corrections of stated facts that are cheap now and expensive to retrofit.

1. **§2.4's decision-table row 2 changes (BSQ-01).** A first claim of an unowned row may take ownership but may not repoint it. Without this, enabling the flag hands every fleet-token holder the URL of every existing production backend on day one, and the `409` guard blocks nothing — because `announced_by` is `NULL` everywhere after `V6`.
2. **`url` is normalized to a bare origin, in `BackendUrlValidator`, on both write paths and at probe time (BSQ-04).** The doc's core blast-radius claim ("only ever `GET {url}/health`") is not true of the current code: `BackendProberImpl` concatenates, so a stored query string swallows `/health` and yields an arbitrary-path GET. This is the single highest-value change in the list and it also makes §6's host:port logging rule coherent.
3. **A registry-size cap on the announce INSERT path (BSQ-03).** The design has no bound on rows announce can create, and `BackendHealthChecker` probes serially with a 10 s read timeout — so an attacker sets the probe-pass duration, and past ~6 rows the pass exceeds its interval and outage detection stops.
4. **The sentinel set gains IP literals, and the mitigation is reframed (BSQ-05).** `^[0-9.]+$` passes the doc's three sentinels and grants the entire IPv4 space. Passing the check must be documented as "not universal", never as "narrow".
5. **The insert-race retry moves outside the transaction (BSQ-08).** BSR-06 as written reproduces the `UnexpectedRollbackException` failure this codebase already documented and fixed once, in `BackendDispatcher`.
6. **BSR-26 is factually wrong and becomes a verification item (§3.5).** `INSERT` on `backends` is already in `DEPLOYMENT.md`'s grant block, table-level. The real grant finding is the opposite: `DELETE` is granted and unused (BSQ-21).
7. **BSR-15 must also touch `WebConfig` (BSQ-11), and its `webhookPattern` precedent does not exist on `master`.** Implemented as literally written, the cap never runs.
8. **The Worker's `403` handling flips from terminal to WARN-and-continue (BSQ-18), and the backoff loop becomes interruptible (BSQ-19).** As written, a Gateway operator flipping the kill switch off crash-loops the whole Worker fleet, and a `SIGTERM` during backoff needs `SIGKILL`.
9. **The allowlist `Pattern` is compiled once at startup with a backtracking budget check (BSQ-06).** BSR-12 makes hand-authored regexes universal across deployments for the first time; the current per-call `String.matches` runs an operator regex against caller-chosen input with no timeout.
