## Verdict: **NEEDS A DEV PASS** — 1 High + 3 Medium must-fix before final verification.

Severity counts: Critical 0 · **High 1** · **Medium 3** · Low 4 · Info 4.

This is a good implementation of a hard feature. The two architecture-level corrections the threat model
demanded most loudly were both genuinely followed, not paraphrased: authorization really does live inside
`authorizeHttpRequests` with `.hasRole("WEBHOOK")` ahead of the surviving `.anyRequest().denyAll()`
(WHT-23 — and the filter does **no** path matching at all, which is the stronger of the two options §4.3
offered), and the webhook body really does contribute only `(projectId, mrIid)` plus a never-persisted
dedup hint (WHT-02 — `GitLabWebhookPayload` does not even *model* `reviewer_ids`/`changes.reviewers`,
which is the right way to make the mistake unavailable to a future maintainer). WHR-21's acceptance
criterion — assert the assembler against `DiffChunker`'s real parser, not against a human reading of the
format — is implemented exactly as specified, table-driven, and it passes. The WHR-15b `X-Gitlab-Size`
`HEAD` check that the §8 probe produced is present, fail-closed on every branch (non-2xx, missing header,
non-numeric header all reject), and correctly picks `head_sha` for a new file and `base_sha` for a
deleted one.

What did not survive the review is the *other* half of §4.2 — the exemption logic, where a check that
looks defensive is actually the widest fail-open path in the feature:

- **F-WH-01 (High):** the "this file is binary, exempt it" test is
  `diff.contains("Binary files") && diff.contains("differ")` — an unanchored two-substring scan of the
  **whole hunk body**. Any ordinary source file whose diff happens to contain both substrings (`differ`
  matches `differs`/`different`/`differently`) is silently dropped from the coverage-bearing set, out of
  the assembled diff, and out of the v3 coverage list — with no exception, no log line, and no metric.
  **Reproduced** against the real `DiffIntegrityVerifier`: a two-file MR where one file removes an
  `isAdmin()` check and contains the comment `// Binary files are handled differently here` yields
  `coverage-bearing files = [src/Other.java]` and an assembled diff that does not mention `Auth.java` at
  all. This is precisely WHT-08/WHT-12's stated end state — "a green security review of code that was
  never sent to the model, indistinguishable from every dashboard from a real clean review" — and it is
  reachable by any MR author, deliberately or by accident.
- **F-WH-02 (Medium):** the "never throws (WHR-07)" contract is enforced by *enumerating* exception
  types, so it is only ever as complete as the last person's enumeration. QA already found one hole in it
  (`RestClientException`) and fixed it at the right place. The remaining hole is one layer up:
  `ReviewService.createReview` — the call the whole orchestrator exists to make — throws
  `DiffTooLargeException` on any oversized MR, and nothing catches it.
- **F-WH-03 (Medium):** WHR-28's "if the notes read fails or is ambiguous, choose *do not post*" is
  implemented backwards; the code posts. Its own javadoc asserts the opposite of what the code does.
- **F-WH-04 (Medium):** a pure rename with unchanged content — `renamed_file: true`, `diff: ""`,
  `old_path != new_path` — matches none of the exemptions and hard-rejects the entire MR with a
  "the diff may be too large or was truncated" comment. WHR-15's exemption list has no rename case.

**AppSec must-fix before merge:** F-WH-01 (High), F-WH-02, F-WH-03, F-WH-04 (Medium).
**Should-fix in the same pass (cheap, same files):** F-WH-05, F-WH-06, F-WH-07, F-WH-08.
**Threat-model amendments this round produces:** F-WH-09 (WHR-19's endpoint list — this answers QA's
open question), F-WH-04 (WHR-15's exemption list), F-WH-10 (the two §7 Semgrep rules).
